## 2. Why this can't be a blind 301 — the loop risk

`middleware.ts`'s WordPress catch-all does a live server-to-server `fetch()` to
`blog.musthavemods.com` on every apex pageview, with `redirect: 'follow'`. If blog.* 301s
*every* request to the apex (proxied or not):

1. Visitor requests `musthavemods.com/<post>/`.
2. Middleware fetches `blog.musthavemods.com/<post>/`.
3. blog.\* 301s to `musthavemods.com/<post>/`.
4. `fetch()` follows it → re-requests `musthavemods.com/<post>/`.
5. Because that's not a Next.js route, Vercel routes it back into the **same middleware**,
   which fetches blog.\* again → step 3.

This is bounded only by `fetch`'s internal max-redirect count, and surfaces as 502s on
**every** proxied article — i.e. the fix would break the 68.9% of Pinterest sessions that
already land correctly on the apex. The redirect must know the difference between "a stranger
requesting blog.\* directly" and "our own proxy fetching blog.\* on a visitor's behalf."

### The exemption signal (shipped in this PR, `middleware.ts`)

Every fetch this middleware makes to blog.\* now carries:

```
X-MHM-Proxy: nextjs-edge
```

on every method (GET/HEAD included), unconditionally — see `MHM_PROXY_HEADER` /
`MHM_PROXY_HEADER_VALUE` near the top of `middleware.ts` and the comment above
`fetchOptions.redirect: 'follow'`. `__tests__/unit/host-split-proxy-header.test.ts` (5 tests)
pins this down: GET, HEAD, category/tag/author archive proxies, and that `redirect: 'follow'`
is unchanged (so genuine WordPress-internal redirects — e.g. a slug change — still work once
the host-split rule correctly exempts this header). This is Tier 2 (middleware routing) but
minimal and behavior-preserving until the BigScoots rule below is applied: today, nothing on
blog.\* checks for this header, so it's inert.

**The BigScoots rule below must redirect only when `X-MHM-Proxy` is absent.** Do not remove
the header from `middleware.ts` without removing the 301 rule first, or every proxied page
502s.

## 3. The caching landmine (empirically confirmed 2026-09-21, live curl against blog.musthavemods.com)

This is the reason a `functions.php`-only fix was reverted once already (comment in
`staging/wordpress/kadence-child-prod/functions.php`, Feb 2026: *"noindex on direct blog
access was unsafe because BigScoots caching cannot distinguish proxied vs direct requests"*),
and the reason the Q6 entry in `operator-queue.md` already flags this as an nginx job, not a
functions.php job. Live headers, 2026-09-21:

```
GET /sims-4-belly-piercing/ (article)         → 200, cache-control: public, s-maxage=31536000, max-age=0, must-revalidate
                                                  x-bigscoots-cache: cache
                                                  cache-tag: blog.musthavemods.com_sims-4-belly-piercing
GET /category/sims-4/ (category)              → 200, same public/s-maxage=31536000 pattern, x-bigscoots-cache: cache
GET /wp-json/                                  → 200, cache-control: private, no-cache, must-revalidate, max-age=0
                                                  x-bigscoots-cache: no-cache
GET /sitemap.xml → 301 → /wp-sitemap.xml → 404 → cache-control: private, no-cache, must-revalidate, max-age=0
                                                  x-bigscoots-cache: no-cache
                                                  x-redirect-by: WordPress
```

Two facts follow directly from this:

1. **Article and category pages are cached for up to a year, keyed by host+path (`cache-tag`),
   not by any request header.** BigScoots' edge (`BigScoots Gateway/1.0.0`) serves a cache HIT
   without ever reaching origin nginx or PHP-FPM. Whichever request type — a direct/bot visitor
   or our own proxy — is the next to hit a MISS for a given URL determines what gets cached
   next; a proxy MISS repopulates a normal public 200 that *all* subsequent requests (including
   direct visitors) then receive from cache, bypassing whatever redirect logic exists at any
   origin layer (nginx or PHP) until the next purge. **This applies equally to the nginx option
   and the functions.php option below — it is not solved by choosing one over the other.**
2. **WordPress's own redirects are naturally excluded from this cache.** The native
   `sitemap.xml → wp-sitemap.xml` 301 above is WordPress-generated (`x-redirect-by: WordPress`)
   and comes back `private, no-cache` / `x-bigscoots-cache: no-cache` — BigScoots respects
   `Cache-Control` from the origin and does not cache non-public responses. This means: **any
   301 we emit, whether from nginx or PHP, is safe from being cached and served to the wrong
   audience, as long as it is explicitly marked `private, no-store`.** The loop risk in §2 is
   about the proxy following a 301 it should have been exempted from, not about the 301 itself
   getting cached and replayed — that risk is closed by explicit `no-store` headers on the
   redirect response in both options below.

**Practical consequence — read this before approving either option:** because article/category
pages are already heavily cached (many popular ones for up to a year), the redirect will not
take effect on a given URL until that URL's cache entry is purged, and its effectiveness will
fade over time as proxy traffic (68.9% of Pinterest sessions to a URL, on average) re-populates
the cache with a plain 200 faster than direct traffic can. **Both options below require an
immediate cache purge after applying, and benefit from a recurring purge (nightly, or reduce
`s-maxage` for article/category paths) to keep re-evaluating the split instead of "sticking" to
whichever request type won the last repopulation race.** This is a real, honest limitation —
not a reason not to ship, since even a partial, decaying redirect converts real weekly sessions
at zero downside once the no-store/no-loop protections are in place, but the operator should
expect the redirect share to need periodic refreshing, not a "set and forget" fix.

## 4. Option A (recommended) — nginx, server-rewrite phase

Runs before location matching and before any cache lookup, on the **origin** vhost for
`blog.musthavemods.com` (the box behind `ssh -i ~/.ssh/bigscoots_staging -p 2222
nginx@74.121.204.122`, used for the Q6 cache purge). Insert directly inside the `server {}`
block, not inside a `location {}` block, and above any existing `location` directives.

nginx's `if` can't express `A AND B AND (C OR D)` in one condition ("if is evil" — each `if`
only conditionally sets a `$variable`, evaluated top to bottom, with no `elif`/`else`). Two
separate flags avoid the trap of a later "this URL shape IS in scope" check accidentally
re-arming a redirect that an earlier "skip" check (proxy header, wrong method) had already
correctly killed — the shape flag can only ever be set by shape rules, and the final decision
only ever downgrades, never re-upgrades, permission:

```nginx
server {
    server_name blog.musthavemods.com;

    # Q13 host-split redirect — see reports/funnel/drafts/host-split-301-2026-09-21.md
    #
    # Step 1: is this URL shaped like an article or a category page at all?
    # ($mhm_shape only ever gets SET to 1 by a positive match, and only ever
    # gets forced back to 0 by an exclusion — never re-armed after that.)
    set $mhm_shape 0;
    if ($uri ~ ^/[^/]+/?$) { set $mhm_shape 1; }        # single path segment = article shape
    if ($uri ~ ^/category/[^/]+/?$) { set $mhm_shape 1; } # /category/<slug>/ = category shape
    if ($uri = "/") { set $mhm_shape 0; }                 # bare homepage is not an article
    if ($uri ~ ^/(wp-admin|wp-json|wp-content|wp-includes|wp-login|xmlrpc|feed|wp-sitemap|sitemap|robots|tag|author|page|date|search)(/|\.|$)) {
        set $mhm_shape 0;                                 # infra / system path — never in scope
    }

    # Step 2: independent of shape, should we skip the redirect entirely?
    set $mhm_skip 0;
    if ($http_x_mhm_proxy != "") { set $mhm_skip 1; }        # our own proxy fetch
    if ($request_method !~ ^(GET|HEAD)$) { set $mhm_skip 1; } # not a page view
    if ($mhm_shape = 0) { set $mhm_skip 1; }                   # wrong shape

    if ($mhm_skip = 0) {
        add_header Cache-Control "private, no-store" always;
        return 301 https://musthavemods.com$uri;
    }

    location / {
        # ... existing directives, unchanged ...
    }
}
```

`add_header Cache-Control "private, no-store" always;` is mandatory (§3) — it's the only thing
stopping BigScoots Gateway from ever caching the 301 itself.

**Scope, spelled out:** matches article slugs (`/<slug>/`) and `/category/<slug>/` only. The
infra regex requires a `/`, `.`, or end-of-string boundary right after the keyword, so it
excludes `/wp-admin/...`, `/wp-json/...`, `/wp-content/...`, `/wp-includes/...`,
`/wp-login.php`, `/xmlrpc.php`, `/feed/`, `/sitemap.xml`, `/wp-sitemap.xml`, `/robots.txt`,
`/tag/*`, `/author/*`, `/page/*` (blog pagination), `/date/*` archives and `/search/` —
**without** false-matching a real article slug that merely starts with one of those words
(e.g. `/feeding-tips/`, `/tagging-cc/`, `/searching-mods/` all keep their trailing character
right after the keyword, which is neither `/`, `.` nor end-of-string, so the boundary check
correctly lets them through). WordPress's native `?s=` search runs on `/` itself, already
excluded by the homepage rule. Anything not matching the narrow article-or-category shape
falls through untouched. This is intentionally conservative — tag/author/date archives get
no redirect in v1; widening scope later (they're lower-traffic and lower-risk once the
article/category rule is proven safe) is a one-line follow-up, not a redesign.

## 5. Option B (fallback) — functions.php

**Not recommended as primary, for the reason in §3: this fires from PHP, which only runs on a
cache MISS — identical effectiveness ceiling to Option A, with none of Option A's
before-cache-lookup timing advantage, and it's the layer that already caused the Feb 2026
noindex-leak revert.** Only use this if nginx config access isn't available. Not applied by
this PR — described here per the task's instructions.

Model: `mhm_seo_301_redirects()` already in `functions.php`, using the existing
`is_from_apex_rewrite()` helper (checks `$_SERVER['HTTP_X_FORWARDED_HOST']`). Add a check for
the new header alongside it:

```php
/**
 * Q13 host-split redirect: blog.* -> apex for direct/bot visitors only.
 * mhm_host_split_301 — CRITICAL_MARKERS entry, do not push without it present
 * in both push-blog-functions*.sh scripts (see scripts/staging/push-blog-functions-prod.sh).
 */
function mhm_host_split_301() {
    if (is_from_apex_rewrite()) {
        return; // our own proxy fetch — X-Forwarded-Host already covers this
    }
    if (!empty($_SERVER['HTTP_X_MHM_PROXY'])) {
        return; // belt and suspenders: explicit proxy header too
    }
    if (!in_array($_SERVER['REQUEST_METHOD'] ?? 'GET', ['GET', 'HEAD'], true)) {
        return;
    }
    if (!is_single() && !is_category()) {
        return; // article + category only, same scope as the nginx version
    }
    $target = home_url(); // resolves to https://musthavemods.com/... given the existing apex overrides
    nocache_headers(); // MANDATORY — without this the 301 can be cached and served to the proxy (see §3)
    wp_safe_redirect($target, 301);
    exit;
}
add_action('template_redirect', 'mhm_host_split_301', 5); // before mhm_seo_301_redirects
```

`nocache_headers()` is a WordPress core function that sends `Cache-Control: no-cache,
must-revalidate, max-age=0` plus `Pragma: no-cache` — the same shape observed on the
already-safe `sitemap.xml` redirect in §3. **Do not ship this without it.**

**CRITICAL_MARKERS to add (describing only, not applying):** add
`"mhm_host_split_301|Host-split 301 (blog.* -> apex, Pinterest consolidation)"` to the
`CRITICAL_MARKERS` array in both `scripts/staging/push-blog-functions-prod.sh` and
`scripts/staging/push-blog-functions.sh`, in the same PR that adds the function, per
CLAUDE.md's rule that routing features get a marker in both scripts.

## 7. Rollback

- **nginx:** delete the inserted block from the vhost `server {}`, reload nginx
  (`nginx -t && systemctl reload nginx` or BigScoots' equivalent). No WordPress involvement,
  no deploy, seconds to revert.
- **functions.php:** `git revert` the commit that added `mhm_host_split_301`, run
  `./scripts/staging/push-blog-functions-prod.sh` (CRITICAL_MARKERS check will pass since the
  marker is removed with the function), then `./scripts/agents/check-blog-sidebar.sh`.
- Either way: purge the BigScoots cache for affected URLs afterward, same command shape as Q6:
  `wp bs_cache purge_cache --urls='https://blog.musthavemods.com/...'`.
